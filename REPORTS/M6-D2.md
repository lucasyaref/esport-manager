# M6-D2 — Character art: LPC role sprites, both team colors

**Status: done.** `tools/check.sh` green (RNG lint, data validation, determinism, viewer `--selftest`). Verified live in the actual match viewer by an independent tester pass — see §4.

## What changed

The procedural placeholder sprite (`game/assets/characters/placeholder.png` — a flat grayscale silhouette, tinted per team at draw time) is replaced by real pixel art: one look per role (top/jungle/mid/carry/support), baked in two team-color variants each, generated from the [Universal LPC Spritesheet Character Generator](https://liberatedpixelcup.github.io/Universal-LPC-Spritesheet-Character-Generator/).

- `game/assets/characters/lpc_<role>_<blue|red>.png` — 10 sheets, 7 rows (idle/run/attack/cast/hurt/die/recall) × 4 cols × 64px.
- `tools/fetch_lpc_sprites.mjs` (+ `tools/package.json`) — regenerates all 10 headlessly, no manual browser step. Re-run it if a role's look changes or a role is added.
- `data/characters.json` — every character gained a `sprite_by_side` field (`{"blue": path, "red": path}`).
- `game/main.gd`, `game/map_view.gd` — texture resolution is now team-aware (see §3).
- `game/anim_config.gd`, `data/animation.json` — sheet frame size 24px → 64px.
- `game/assets/characters/LPC_NOTICE.txt` (new) — attribution, regenerated by `tools/fetch_lpc_sprites.mjs` itself from the generator's own "Credits (TXT)" export for every selection used (not a hand-summary): full per-asset author/license/link entries. The art is CC-BY-SA-3.0/GPL-3.0/OGA-BY-3.0 per item (a few pieces are CC0), not blanket CC0.

Role looks: **top** = spear, plain short hair. **jungle** = dagger, hood. **mid** = staff, long hair, no hat. **carry** = bow, ponytail. **support** = same staff as mid, but a hat — the hat is deliberately the entire distinguishing signal in that pair, per the designer's requirement that top/jungle and mid/support each read apart at a glance.

## Why this took more than "download and wire it up"

**The generator is fully scriptable, no browser extension needed.** Everything here runs headlessly via Playwright driving a locally-cached Chromium — character configuration through the URL hash, and (more importantly) reading the final render straight off the canvas the app exposes at `window.canvasRenderer` for its own PNG download button. No manual step, nothing that needed "Claude in Chrome."

**Reading the small on-page animation preview would have shipped silently-wrong art.** It looks like a 4-frame animation strip; reading the app's own source (`sources/canvas/preview-animation.ts`) shows it actually redraws one arbitrary cycle-frame across all 4 *directions*, stacked side by side, live on a `requestAnimationFrame` loop — screenshotting it mid-cycle gives four different facings at one pose, not a usable frame sequence. Caught before any asset was built from it, by reading the generator's source rather than trusting the visual. The fix: read exact `(row, column)` offsets out of the real full-character canvas, per the row math in `sources/state/constants.ts`' `ANIMATION_CONFIGS` (`row = animation block start + direction index`, `DIRECTIONS = [up, left, down, right]` → "down" = the front-on facing this game already draws, flipped for the other side).

**Two per-item compatibility gaps, both caught by rendering and looking, not by trusting the generator's "Current Selections" panel:**
- Arming Sword's only working swing is `slash_128` — an oversized 128px frame, double every other row's size, which would have forced a per-row frame-size exception. Swapped Top to a Spear (`thrust`, a normal 64px frame).
- A black hat on black hair was invisible at this frame size on the first Support pass. Swapped to tan.

**`--selftest` caught a real design gap of my own.** I initially dropped `die`/`recall` as sheet rows, reasoning the runtime row-lookup fallback (row not found → draws idle) was an acceptable substitute for `recall` and that `die` was handled by a separate procedural fallback path. The project's own `--selftest` disagreed — it hard-asserts every `anim_state` the game can ever assign has a real sheet row, for both. Fixed by keeping both as real rows, built from frames of an animation the generator does have (`die` = `hurt`'s later, more-collapsed columns, held; `recall` = `idle` verbatim, since the separate recall ring VFX is what actually reads as "channeling").

**A real correctness bug, not a hypothetical:** `data/players.json`'s `champion_pool` is per-role, and both sides' same-role players draw from the *identical* pool (e.g. `azw_top` and `crv_top` can both roll "bastion"). With team color previously applied by runtime tint, a shared texture cache keyed only by `char_id` was fine. With team color now baked into the file, that same key would silently hand one side's mirrored pick the other side's colors. Fixed by keying `main.gd`'s texture cache (and `map_view.gd`'s two lookups) on `char_id + team`.

## Verification

1. `tools/check.sh` — RNG lint, data validation, determinism (3 seeds, bit-identical), viewer `--selftest` (asserts every anim_state has a sheet row, among everything it already checked) — all green.
2. Every generated sheet spot-checked directly (all 7 poses render correctly, correct team color, roles read as distinct).
3. Independent tester pass, live in the actual running match viewer (not just headless stats) — real texture, blue vs red confirmed side by side in the same frame, all 5 roles visually distinct, badges/HP-bar aligned at normal zoom, no console errors, no missing textures. `die` row confirmed correct from the source art and the (unchanged) draw path, though the tester didn't land a live screenshot in the ~20-tick window before the fountain treatment takes over.

## One follow-up flagged, not fixed here

At high camera zoom (~3.6+, near the auto-camera director's own 3.2–4.0 range), the level badge and role-letter badge — flat-pixel circles that scale up to 3× with zoom — grow large enough to cover a bigger share of the new, visually smaller LPC body than they did over the old placeholder's silhouette. Not broken or clipped, just oversized relative to the new art. The badge-sizing formula (`map_view.gd`, `_zoom_mult`) was tuned against the placeholder's proportions and hasn't been revisited since. Left as-is pending a look — didn't want to tune it blind without the designer seeing the new art first.

## Open design decision, on record in BACKLOG

This ships **role-level** art (one look × 5 roles), not per-character. The designer's stated long-term intent is **one real sprite per character** — `sprite_by_side`/`sprite` already resolve per character id, so that migration is a data change (new paths) plus, if per-character art doesn't need team-color baking, possibly dropping back to runtime tint — no architectural rework.
